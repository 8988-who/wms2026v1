# 项目开发规范指南

> 适用范围：本项目（WMS）后端（Spring Boot 4 / JDK 17 / MyBatis-Plus）与配套前端协作。
> 强制级图例：【强制】必须遵守，违反视为缺陷；【推荐】默认遵守，特殊情况需评审说明；【建议】视场景采纳。
> 数据库设计细则见同目录《数据库设计规范.md》。
> 版本：v1.1　整理日期：2026-08-10

---

## 一、命名与代码风格【强制】

- **包名**：全小写，点分隔，如 `com.company.module.sub`。
- **类 / 接口 / 枚举**：大驼峰（UpperCamelCase），名词或名词短语。
- **方法 / 变量**：小驼峰（lowerCamelCase），动词或动宾短语。
- **常量**（`static final`）：全大写，下划线分隔。
- **布尔变量**：一律以 `is` / `has` / `can` 开头，禁止使用 `flag` 等无意义命名。
- **缩进**：统一 4 个空格，禁止使用 Tab 键。
- **行宽**：不超过 150 字符（建议 120）。
- **IDE 配置**：所有成员必须导入同一份 `.editorconfig` 或格式化模板，提交前自动格式化。
  > 注：后端 `wms/` 模块当前缺少 `.editorconfig`，需补齐并接入 spotless/checkstyle。

---

## 二、注释与文档规范【推荐】

- **类级注释**：必须包含功能描述、作者、创建日期；复杂类需注明线程安全性。
- **公开方法**（`public`）：必须写 Javadoc，说明参数、返回值、可能抛出的异常。
- **私有方法**：逻辑复杂时添加注释，简单 getter/setter 可省略。
- **注释内容**：只解释"为什么做"（业务背景、权衡决策），不重复代码行为。
- **废弃代码**：一律直接删除，禁止注释后堆砌，利用 Git 历史找回。
- **TODO / FIXME**：必须标注负责人和预期完成日期。
  ```text
  // TODO(张三, 2026-09-01): 后续接入新缓存策略
  ```

## 三、异常处理规范【强制】

- **统一异常类**：所有业务异常必须继承自定义 `BusinessException`，并携带错误码。
- **全局拦截**：使用 `@RestControllerAdvice` 统一处理异常，返回固定 JSON 结构（`code` + `msg` + `data`）。
- **禁止行为**：
  - 不允许 catch 后不做任何处理（吞异常）。
  - 不允许 `e.printStackTrace()`（线上会污染日志）。
  - 不允许在 `finally` 中抛出不受检异常。
- **异常粒度**：方法抛出的异常需在方法签名或注释中明确列出（除 `RuntimeException` 外）。

## 四、日志规范【强制】

- **日志级别标准**：
  | 级别 | 使用场景 |
  |------|----------|
  | `ERROR` | 需立即人工介入的系统故障（如 DB 连不上、核心依赖不可用） |
  | `WARN` | 可自动恢复或降级的异常（如外部接口超时后重试成功） |
  | `INFO` | 核心业务里程碑（如订单创建、支付回调），**严禁在循环内打印 INFO** |
  | `DEBUG` | 仅开发/测试环境开启，用于调试参数 |
- **日志内容**：必须包含关键业务标识（如 `userId`、`orderId`），便于链路追踪；打印异常时保留堆栈（`log.error("msg", e)`），勿只打 `e.getMessage()`。
- **敏感信息**：禁止打印身份证号、手机号全号、密码、密钥等，需脱敏（如手机号显示 `138****1234`）。
- **日志框架**：统一使用 SLF4J + Logback，禁止使用 `System.out`。

## 五、数据库与 SQL 规范【强制】

> 完整细则（前缀分治、字段类型、约束索引、触发器、实体映射、DDL 变更、模板）见《数据库设计规范.md》，本节仅列核心红线。

- **表名**：小写字母 + 下划线，单数形式（如 `wms_cart_item`），禁止使用 `tbl_` 前缀。
- **必备字段**（按表前缀分治，替代原通用 `gmt_*` 约定）：
  - `sys_` 脚手架表：沿用框架原生命名（`create_time` / `update_time` / `create_by` / `update_by` / `is_deleted`），**保持原样不动**。
  - `wms_` / `api_` 自研表：统一 `id`（int8 序列） + `created_time` / `updated_time` / `created_by` / `updated_by` + `is_deleted`（0-未删除，1-已删除），作为项目及后续开发的**唯一标准**。
  - 所有业务表**必须含 `is_deleted`** 并配 `@TableLogic`，禁止对业务数据物理 `DELETE`。
- **字段类型**：时间用 `timestamp(6)`（如需时区用 `timestamptz`）；布尔/状态用 `int2`；主键/外键用 `int8`。
- **SQL 写法**：
  - 禁止 `SELECT *`，必须显式列出所需字段。
  - `UPDATE` / `DELETE` 必须带 `WHERE` 条件，优先使用主键或索引字段。
  - 连表查询不建议超过 3 张表，复杂查询拆解为多次单表查询 + 应用层组装。
  - MyBatis-Plus **禁止 `${}` 拼接参数**（防 SQL 注入），必须用 `#{}`；动态排序字段须走白名单校验。
- **索引规范**：对高频查询字段建立合适索引，单表索引数不超过 5 个（含唯一约束隐含索引）。

## 六、Redis 与缓存规范【推荐】

- **Key 命名**：统一使用业务前缀 + 冒号 + 标识，如 `user:info:{userId}`、`order:detail:{orderId}`。
- **过期时间**：所有缓存必须设置合理的 TTL（如 30 分钟），避免内存堆积。
- **缓存更新**：遵循"先更新数据库，再删除缓存"或"延迟双删"策略，保证最终一致性。
- **缓存穿透**：对不存在的数据也应缓存空值（过期时间短）或使用布隆过滤器。
- **缓存雪崩**：批量设置过期时间时，增加随机偏移量。
- **使用场景**：仅缓存读多写少、对实时性要求不高的数据，严禁缓存频繁变更的数据。

## 七、MinIO 文件存储规范【推荐】

- **Bucket 命名**：全小写，使用连字符分隔，如 `project-avatar`、`project-doc`。
- **文件路径**：按业务/日期分层，如 `avatar/2026/08/10/uuid.jpg`，避免单目录文件过多。
- **文件命名**：使用 UUID + 原始后缀，确保全局唯一，**禁止直接使用用户上传的原始文件名**。
- **访问权限**：默认私有，临时 URL 需带有效期（如 7 天），禁止永久公开链接与桶公共读写。
- **上传校验**：前端上传前校验文件大小、类型；后端二次校验并限制（如图片 < 5MB），类型走白名单。
- **异常处理**：上传失败必须记录日志并返回明确错误信息，不得直接抛出原始异常。

## 八、Git 协作规范【强制】

- **分支模型**：`main`（生产） + `dev`（开发） + `feature/*`（功能） + `hotfix/*`（紧急修复）。
- **分支命名**：
  - `feature/功能简述`，如 `feature/user-login`
  - `hotfix/修复简述`，如 `hotfix/payment-timeout`
- **提交信息**（Commit Message）：遵循约定式提交格式：
  ```text
  <type>(<scope>): <subject>
  ```
  - `type`：`feat` / `fix` / `docs` / `style` / `refactor` / `test` / `chore`
  - `scope`：可选，模块名称
  - `subject`：简短描述，不超过 50 字符
  - 示例：`feat(order): add auto-cancel expired orders`
- **合并要求**：
  - 禁止直接 push 到 `main` 或 `dev`。
  - 所有代码合并必须通过 Pull Request（PR），且至少 1 名 Reviewer 批准。
  - PR 描述需填写：改动点、影响范围、测试情况。
- **提交粒度**：每次提交应保持逻辑完整，避免将多个不相关改动混在一起。

## 九、测试规范【推荐】

- **单元测试**：核心工具类、算法、业务逻辑层（Service）覆盖率不低于 70%。
- **测试命名**：采用 `should_预期行为_when_条件` 格式，如 `should_throwException_when_userIdIsNull`。
- **测试环境**：单元测试使用 H2 或内存数据库；集成测试（涉及 DB/Redis/MinIO）单独标记，不在 CI 快速阶段运行。
- **端到端测试**：关键业务流程（如登录 → 下单 → 支付）需编写集成测试，并定期在预发布环境回归。
  > 注：后端 `wms/src/test` 当前不存在测试，属零覆盖，需优先补齐核心 Service 测试。

## 十、安全底线【死红线】

- **SQL 注入**：必须使用参数化查询（MyBatis-Plus 的 `#{}`），禁止任何字符串拼接。
- **敏感配置**：密码、密钥、Token 禁止硬编码在代码中，必须使用环境变量或配置中心（如 Apollo/Nacos）。
- **用户数据脱敏**：日志、返回体、前端展示中，对身份证、手机号、银行卡号等必须脱敏。
- **权限控制**：所有业务接口必须经过身份认证和权限校验（Spring Security 或自定义拦截器）。
- **文件上传**：禁止直接使用用户文件名，限制文件类型（白名单），存储路径不可被遍历。

---

## 十一、开发流程与质量门禁【建议】

- **Code Review 检查项**（Reviewer 重点关注）：
  - 是否符合命名、注释、异常、日志规范
  - 是否有潜在性能问题（如 N+1 查询、未使用索引）
  - 是否有缓存一致性问题
  - 是否编写了必要的测试
- **CI 门禁**（持续集成阶段）：
  - 编译成功、单元测试通过
  - 代码静态扫描（SonarQube）无阻断项（如严重漏洞、坏味道超过阈值）
- **上线前检查**：必须验证数据库变更脚本、缓存清理方案、回滚方案是否就绪。

---

## 十二、规范执行与维护

- **脚手架固化**：将上述规范内化为项目脚手架（如 Maven Archetype），新项目自动继承。
- **定期抽查**：每周随机抽查 3 个 PR，发现严重违规者提醒并记录，纳入团队质量考核。
- **规范更新**：当技术栈或业务变化时，由团队共同修订本指南，版本号递增。
